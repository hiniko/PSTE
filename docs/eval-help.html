Reading a test run

A test run page shows the same corpus document under three arms, with every violation marked. This page explains what each part means.

A conformance result is not a measure of quality. Nobody has yet run a reading trial with people. This page explains what the viewer shows, not what the numbers prove.

The three arms

Each document goes through three arms, plus the source column. Every arm answers the same request, so a difference between arms is the difference the request made.

  • Source. The committed document. It is not generated, and every rewrite starts here.
  • Control. A plain request to simplify the text. It carries no other instruction.
  • PSTE. The same plain request. This arm also carries the PSTE skill.
  • PSTE, fixed. The PSTE arm's draft. One fix pass then ran against the rule check's own violations.

The comparison that matters is PSTE against control. Both get the same request. The skill is the only difference, so a gap between the two arms is the skill's own effect.

A violation and a rule

A violation is one place in the text where the rule check or the judge says a rule broke. Click a violation in the list, and the matching span highlights in the text above it.

Each violation names a rule, such as PSTE-N5 or PSTE-A1. PSTE-1 numbers every rule. A rule identifier lets a reader find the exact clause a violation cites, instead of a paraphrase of it.

Mechanical and judged violations

Two different things write violations, the rule check and the judge, and the page marks them apart.

A mechanical violation comes from pste_lint.py, a fixed set of pattern checks. It runs in a fraction of a second, and it gives the same response every time. It implements 29 of PSTE-1's 70 rules, the ones a pattern can catch without judging meaning.

A judged violation comes from a language model reading the text, under "Judge violations" on the page. It covers rules a pattern cannot decide, such as whether a sentence names its actor or buries an instruction inside a description. It runs slower, costs money to call, and a repeat run can reach a different response on the same text.

Agreement ratios

A judged violation shows a ratio such as 4/5. The judge read the same text on five separate passes, and confirmed the violation on four of those passes.

A single model call is one opinion, not a measurement. Asking repeatedly and counting agreement is how the page shows that a judge can disagree with itself between runs on the same fixed text. A violation needs agreement at or above a set gate to count as CONFIRMED and count toward the weighted cost. A violation below the gate shows as LOW AGREEMENT, and a violation the judge considered and dismissed shows as REJECTED. Both stay visible, for a reader to audit the judge, but neither affects the weighted cost.

A run can also send a document to more than one judge model. When every judge that ran on a document confirms the same rule, that violation shows as OVERLAP: the strongest form of agreement, because two separate models agree and not one model agreeing with its earlier self.

The fact-loss gate

A rewrite can follow every rule by leaving something out. Fewer facts means fewer words, and fewer words means fewer chances to break a rule.

The fact-loss check compares a rewrite against its source, and looks for a dropped number, unit, identifier, negation, or obligation. A rewrite that drops one of these is marked FACT LOSS, regardless of how clean its other violations read. This check catches a missing token. It does not read for a changed meaning, so a clean result here is not proof that a rewrite stayed faithful.

Weighted cost

Not every broken rule costs a reader the same. PSTE-1 assigns each rule a weight from 0 to 1: a dropped fact carries the full weight of 1.0, and a missing hyphen carries 0.1.

The weighted cost sums each violation's own weight. Ten trivial violations and one dropped fact do not then read as the same size of fault. It stays a conformance count, not a quality score. A low weighted cost says the broken rules cost little by PSTE-1's own scale. It says nothing about whether the prose reads well.

A cell with a weighted cost of 0 carries no countable mechanical violation, no fact loss, and no confirmed judged violation. That holds for this one run only. It is not a claim that the text reads well. It is not a claim that a person finds it easier.

Clean-sentence rate

PSTE counts by the sentence. The word limits in N1 and N2 are sentence rules, and so is the six-sentence limit in D2. A reader meets the text one sentence at a time.

The clean-sentence rate is the share of sentences with no violation at all. A document-level percentage hides a difference that matters. Ten violations crowded into one sentence and ten violations shared across ten sentences are not the same fault.

UNJUDGED and NOT JUDGED

A cell can go unchecked by the judge entirely. The page marks this apart from an ordinary violation, so a reader never mistakes an unchecked document for one the judge read and rejected.

UNJUDGED means the judge step ran, but every call for this one cell failed, most often an API limit. The mechanical and fact-loss checks still ran. Over half of PSTE-1's rules need a judge, and none of them got checked here.

NOT JUDGED means this cell was never sent to a judge at all. A large run judges a fixed set of anchor documents every time, and rotates the judge across the rest to control cost. A NOT JUDGED cell was excluded by that plan, not by an error.

Neither state counts as clean. Both mean the same thing to a reader: this text has not been checked against the rules that need a judge, so no weighted cost can be claimed complete for it yet.

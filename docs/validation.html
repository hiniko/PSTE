Validation

This project uses the word "checker" for two different tools. This page keeps them apart, and shows how PSTE gets tested.

Two different checkers

A checker at evals/pste_lint.py checks one document. A writer runs it against a single file, and it reports every finding with its weight and a weighted total. It is a tool, like a linter.

The eval suite is a different thing. It tests whether PSTE itself works: whether the skill beats a plain request, whether a fix pass helps, and whether any of that costs the reader a fact. The suite uses a corpus, three arms, a judge, and a fact-loss gate.

The corpus, and where it came from

The corpus holds 13 documents. Eight are real documents that people wrote for real projects. Five are synthetic: a model wrote them, in a clean container, each one grounded in a fetch of a real upstream page.

Four licenses appear in the corpus: CC-BY-4.0, Apache-2.0, BSD-3-Clause, and CC0-1.0. Every document carries its URL, its author, and its attribution. The tooling refuses a license outside the allowed set.

Browse the corpus to see every document, its type, and its license.

How a run works

Each run tries three arms against the same corpus document. A plain request asks a model to simplify the text, with no other instruction. The skill arm adds the PSTE skill to the same request. A third arm takes the skill's draft and runs one fix pass against the checker's findings.

The comparison that matters is the skill against the plain request. Both get the same ask. The skill is the only difference, so a gap between them is the skill's effect.

A fix pass can remove a fact to satisfy a rule. A fact-loss gate catches this: when a fix drops a fact the draft still had, the run keeps the draft and discards the fix. A judge model then reads every draft and confirms or rejects the findings the mechanical checker could not decide alone.

How the project verifies itself

Twelve scripts in this repository carry a self-test flag, which runs a fixed set of cases and needs no network call and no model. A separate check compares every corpus file against its recorded checksum, and another compares the generated word-list appendices against their source.

None of these checks costs money, and none depends on a model being available.

What the numbers say, and what they do not

A checker can count rule violations. It cannot measure whether a person reads the text more easily. Nobody ran a reading trial with people yet.

The numbers below report one thing: the share of sentences in the corpus that carry no finding from a checker. That checker implements 29 of PSTE-1's 70 rules. The count is not a quality score, and PSTE-1 itself says so.

Source documents, as published47.5

The source documents, as published, leave 47.5 sentences clean in every hundred. A plain request to simplify them reaches 73.6. The skill reaches 83.9. The skill, plus a fix pass against the checker's findings, reaches 96.0.

What is known, and what is not

A conformance result is not a measure of quality. No reading trial with people ran yet. Until one runs, the honest claim is that this text passes automatic checks. It is not that this text is easier to read. Read the trial design.

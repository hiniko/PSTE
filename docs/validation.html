Validation

This page shows how PSTE gets tested: a rule check that counts what a pattern can find, and a judge that reads what a pattern cannot.

The rule check, and the judge

The rule check runs at evals/pste_lint.py, against one document. A writer runs it against a single file, and it reports every violation with its weight and a weighted total.

The test suite is a different thing. It tests whether PSTE itself works: whether the skill beats a plain request, whether a fix pass helps, and whether any of that costs the reader a fact. The suite uses a corpus, three arms, a judge, and a fact-loss gate.

The corpus, and where it came from

The corpus holds 13 documents. Eight are real documents that people wrote for real projects. Five are synthetic: a model wrote them, in a clean container, each one grounded in a fetch of a real upstream page.

Four licenses appear in the corpus: CC-BY-4.0, Apache-2.0, BSD-3-Clause, and CC0-1.0. Every document carries its URL, its author, and its attribution. The tooling refuses a license outside the allowed set.

Browse the corpus to see every document, its type, and its license.

How a run works

Each run tries three arms against the same corpus document. A plain request asks a model to simplify the text, with no other instruction. The skill arm adds the PSTE skill to the same request. A third arm takes the skill's draft and runs one fix pass against the rule check's violations.

The comparison that matters is the skill against the plain request. Both get the same ask. The skill is the only difference, so a gap between them is the skill's effect.

A fix pass can remove a fact to satisfy a rule. A fact-loss gate catches this: when a fix drops a fact the draft still had, the run keeps the draft and discards the fix. A judge model then reads every draft and confirms or rejects the violations the rule check could not decide alone.

How the project verifies itself

Twelve scripts in this repository carry a self-test flag, which runs a fixed set of cases and needs no network call and no model. A separate check compares every corpus file against its recorded checksum, and another compares the generated word-list appendices against their source.

None of these checks costs money, and none depends on a model being available.

What the numbers say, and what they do not

The rule check can count rule violations. It cannot measure whether a person reads the text more easily. Nobody ran a reading trial with people yet.

The numbers below report one thing: the share of sentences in the corpus that carry no violation from the rule check. The rule check implements 29 of PSTE-1's 70 rules. The count is not a quality score, and PSTE-1 itself says so.

What is known, and what is not

A conformance result is not a measure of quality. No reading trial with people ran yet. Until one runs, the honest claim is that this text passes automatic checks. It is not that this text is easier to read. Read the trial design.

The agent transformer is still under test

PSTE has a second use: it can also govern the text an agent writes back to you, turn after turn, inside a conversation. This use is experimental. The corpus above tests one pass over one document. No run until now tested a long conversation.

What was measured

One session asked fifty questions in order. The questions moved from HTTP down through TLS, TCP, IP, the link layer, the operating system, and into debugging. Two arms answered the same fifty questions. One arm read the rules first. The other arm never saw them.

Neither arm revised a response afterward. Neither arm ran any check over its own text.

What the shape means

The PSTE arm rises across the first third of the session, then holds. The middle third and the last third differ by 0.03, a change worth calling nothing. So the PSTE arm's rate change across the session is a step, not a slope. The arm without PSTE stays flat across all three thirds, so the questions did not increase in difficulty as the session went on.

The honest comparison

A single pass over one document reaches a rate far below 4.4 violations per 100 words. This conversational use is measurably worse than the document case. The project does not yet know why the step happens, or how to remove it.

What is known about the cause

Nothing here is proven. Two ideas are worth naming as open questions, not as violations.

The rule set may be too large for a model to hold in attention across a long session. That is the first open question. The per-turn reminder may be too short to anchor behavior on its own. That is the second. Neither idea has support yet beyond the shape above.

What other tools do

PSTE is not the only project that meets this pattern. The caveman plugin for Claude Code carries a comment in its own activation hook. The comment reads, verbatim: "The old 2-sentence summary was too weak — models drifted back to verbose mid-conversation, especially after context compression pruned it away. Full rules with examples anchor behavior much more reliably."

The caveman plugin's whole rule set is 3,653 characters. PSTE's rule set is 16,617 characters. A smaller rule set costs a tool less to re-inject across a session.

This comment is evidence that the pattern is not unique to this project. It is also evidence that rule-set size affects how cheaply a tool can fight the drift.

What would settle it

Open work remains, with no date attached to any of it. One path is progressive disclosure: load more rules only when a session needs them, which first needs a way to detect that need. A second path is re-injection: write part of the rule set back into context every few turns, not only at the start.

A third path tests a smaller rule set and a shorter per-turn reminder against the current pair. A fourth path runs these same fifty questions again, to learn whether the step reproduces.

The limit that still holds

None of this measures whether a reader understands the text better. evals/FUTURE-WORK.md holds that trial design.

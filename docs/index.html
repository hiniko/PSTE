Programming Simplified Technical English

This page follows PSTE. You read an example, not a demo.

What PSTE is

PSTE is a controlled English for prose about software. It sets a restricted vocabulary and a fixed grammar. A tired reader gets the fact without decoding the sentence. A reader whose first language is not English gets the same result.

PSTE governs form, not substance. It does not change what a writer knows, only how a writer says it.

A sentence follows fixed limits. An instruction stays under 20 words. A description stays under 25. A paragraph holds six sentences at most.

The verb stays active, and the actor stays named.

Read the full specification on this site, or spec/PSTE-1.md on GitHub. The short version is spec/STANDARD.md on GitHub.

Example

The passage below comes from the published Caddy documentation. The skill rewrote it, and then corrected the rewrite.

Before
Caddy doesn't need a special "enable HTTPS" switch. It turns on automatic HTTPS the moment it sees a domain name or IP address somewhere in your configuration — a site address in the Caddyfile, a host matcher in a JSON route, a --domain or --from flag on the command line, or a name in the automate certificate loader.
After
Caddy has no "enable HTTPS" switch. It turns on automatic HTTPS when it finds a domain name or an IP address in your configuration. Caddy looks in these places: - a site address in the Caddyfile - a host matcher in a JSON route - a --domain or --from flag on the command line - a name in the automate certificate loader

What changed, and why

The published text broke four rules. A contraction broke rule PSTE-N3, no contractions. An em dash joining two clauses broke rule PSTE-X5, the em dash rule.

The long opening sentence broke rule PSTE-N2, the 25-word limit. Naming four places inside one sentence broke rule PSTE-D4, the three-item list rule.

The rewrite fixed all four. "Does not" replaced the contraction. The em dash became two sentences. The long sentence split into a short sentence and a list. The four places became four list items.

Controlling agent output (experimental)

Every example above is a document. PSTE also controls something else: the text an agent writes back to you, turn after turn, inside a conversation. This use is experimental, not tested the way the document case is.

It costs far more context. A fifty-turn measurement also found more violations, at a less steady rate, than one document pass gets. Read the measurement.

Below, two agents respond to the same opening question from a real eight-turn conversation: "How does HTTP work when I type a URL into the browser and hit enter?" One agent was forbidden from reading the rules. The other read them first. Compare the register, not the facts.

Without PSTE
A bunch of stuff happens fast. First the browser parses the URL to pull out the scheme, host, port, and path. Then it needs an IP address for that host, so it does a DNS lookup — checks its own cache, then the OS cache, then asks a resolver (usually your ISP's or something like 1.1.1.1) which walks the DNS hierarchy if it doesn't already know the answer. Once it has an IP, the browser opens a TCP connection to that address on port 443 (or 80 for plain HTTP). That's the three-way handshake. If it's HTTPS — which is almost everything now — a TLS handshake happens on top of that TCP connection to negotiate encryption and verify the server's certificate. With a secure channel established, the browser sends an HTTP request: a method like GET, the path, headers (cookies, user-agent, accept-encoding, etc.), and a body if there is one. The server processes that, maybe hits a database, renders something, and sends back a response — a status code, headers, and a body, usually HTML. The browser then parses that HTML, discovers it needs more resources (CSS, JS, images), and fires off more requests for those, often reusing the same TCP connection since HTTP/1.1 and later support keep-alive. Then it builds the DOM, runs layout, paints pixels, executes scripts. That's the whole pipeline, DNS to pixels. Want me to go deeper on any one stage?
With PSTE
The browser turns the domain name into an IP address, opens a connection to the server, and sends an HTTP request over it. Four steps happen in order. 1. The browser checks its cache for the IP address of the domain. If the cache has no entry, the browser asks a DNS resolver. 2. The browser opens a TCP connection to that IP address, on port 443 for HTTPS. This step is the handshake. 3. The browser and the server run a TLS handshake over the TCP connection. This step agrees on encryption keys and checks the identity of the server. 4. The browser sends the HTTP request inside the encrypted connection. The server sends back a status code, headers, and the body. The browser reads the response, then renders the HTML. A page with embedded images, scripts, or fonts causes more requests, one per resource. Many of these requests reuse the same connection, so they skip steps 2 and 3. I did not cover HTTP/3, which replaces TCP with QUIC. The flow above holds for HTTP/1.1 and HTTP/2, which still run over TCP.

One question, one model, one topic. This shows the register a reader gets, not that a reader understands the response better. See the same effect hold across the full eight-turn conversation, with the measurements.

Get PSTE

PSTE is a plugin for Claude Code. The repository is also a plugin marketplace, so two commands install it. Run them inside Claude Code:

/plugin marketplace add hiniko/PSTE
/plugin install pste@hiniko

The first command adds the marketplace. The second installs the plugin from it. The Install page covers the hand-install path, turning the skill on, and what it costs in context.

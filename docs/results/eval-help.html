Reading an eval page

An eval page shows the same corpus document under three arms, with every finding marked. This page explains what each part means.

A conformance result is not a measure of quality. Nobody has yet run a reading trial with people. This page explains what the viewer shows, not what the numbers prove.

The three arms

Each document goes through three arms, plus the source column. Every arm answers the same request, so a difference between arms is the difference the request made.

  • Source. The committed document. It is not generated, and every rewrite starts here.
  • Control. A plain request to simplify the text. It carries no other instruction.
  • PSTE. The same plain request. This arm also carries the PSTE skill.
  • PSTE, fixed. The PSTE arm's draft. One fix pass then ran against the checker's own findings.

The comparison that matters is PSTE against control. Both get the same request. The skill is the only difference, so a gap between the two arms is the skill's own effect.

A finding and a rule

A finding is one place in the text where a checker says a rule broke. Click a finding in the list, and the matching span highlights in the text above it.

Each finding names a rule, such as PSTE-N5 or PSTE-A1. The standard, PSTE-1, numbers every rule. A rule identifier lets a reader find the exact clause a finding cites, rather than a paraphrase of it.

Mechanical and judged findings

Two different checkers write findings, and the page marks them apart.

A mechanical finding comes from pste_lint.py, a fixed set of pattern checks. It runs in a fraction of a second, and it gives the same answer every time. It implements 29 of the standard's 78 rules, the ones a pattern can catch without judging meaning.

A judged finding comes from a language model reading the text, under "Judge findings" on the page. It covers rules a pattern cannot decide, such as whether a sentence names its actor or buries an instruction inside a description. It runs slower, costs money to call, and a repeat run can reach a different answer on the same text.

Agreement ratios

A judged finding shows a ratio such as 4/5. The judge read the same text on five separate passes, and confirmed the finding on four of those passes.

A single model call is one opinion, not a measurement. Asking several times and counting agreement is how the page shows that a judge can disagree with itself between runs on the same fixed text. A finding needs agreement at or above a set gate to count as CONFIRMED and affect PASS or FAIL. A finding below the gate shows as LOW AGREEMENT, and a finding the judge considered and dismissed shows as REJECTED. Both stay visible, for a reader to audit the judge, but neither affects the verdict.

A run can also send a document to more than one judge model. When every judge that ran on a document confirms the same rule, that finding shows as OVERLAP: the strongest form of agreement, because two separate models agree and not one model agreeing with its earlier self.

The fact-loss gate

A rewrite can pass every conformance rule by leaving something out. Fewer facts means fewer words, and fewer words means fewer chances to break a rule.

The fact-loss check compares a rewrite against its source, and looks for a dropped number, unit, identifier, negation, or obligation. A rewrite that drops one of these fails, marked FACT LOSS, regardless of how clean its other findings read. This check catches a missing token. It does not read for a changed meaning, so a clean result here is not proof that a rewrite stayed faithful.

Weights, and why they differ

Not every broken rule costs a reader the same. The standard assigns each rule a weight from 0 to 1: a dropped fact carries the full weight of 1.0, and a missing hyphen carries 0.1.

The weighted total sums each finding's own weight. Ten trivial findings and one dropped fact do not then read as the same size of problem. It stays a conformance count, not a quality score. A low weighted total says the broken rules cost little by the standard's own scale. It says nothing about whether the prose reads well.

PASS and FAIL

PASS means one thing: this arm's text carries no countable mechanical finding, no fact loss, and no confirmed judged finding, on this one run. It is not a claim that the text reads well, and it is not a claim that a person would find it easier.

FAIL means at least one of those three checks caught something. The findings and the judge's reasons sit beside the verdict, so a reader sees exactly what to fix rather than a bare score.

UNJUDGED and NOT JUDGED

A cell can fail to reach a verdict at all. The page marks this apart from FAIL, so a reader never mistakes an unchecked document for one the judge read and rejected.

UNJUDGED means the judge stage ran, but every call for this one cell failed, most often an API limit. The mechanical and fact-loss checks still ran. Over half the standard's rules need a judge, and none of them got checked here.

NOT JUDGED means this cell was never sent to a judge at all. A large run judges a fixed set of anchor documents every time, and rotates the judge across the rest to control cost. A NOT JUDGED cell was excluded by that plan, not by an error.

Neither state counts as a pass. Both mean the same thing to a reader: this text has not been checked against the rules that need a judge, and no verdict can be claimed for it yet.
